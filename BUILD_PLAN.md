## 1. What we are building (one paragraph)

RouteLab is a web console for developers who add AI features to Firebase apps. For each feature, the developer pastes a prompt and a set of real test inputs. RouteLab runs every input through Firebase AI Logic twice: forced on-device (`ONLY_ON_DEVICE`, Gemini Nano in Chrome) and forced to the cloud (`ONLY_IN_CLOUD`). It grades both, records refusals, schema failures, timeouts and freezes, latency and estimated cost, and gives a per-feature verdict (on-device first, cloud only, or a length-based split). One click on **Apply** publishes that routing to **Firebase Remote Config**, and a companion demo app picks it up without a redeploy.

**Why it can win:** the judges are the Firebase AI Logic team. Our own testing found Gemini Nano scoring 24/24 on mild synthetic moderation samples, then allowing 5 of 11 real toxic comments and freezing on a 67-character comment until Chrome was restarted. RouteLab is the tool that catches that before shipping. That is measured, honest, non-obvious use of hybrid inference.

## 2. Architecture

```
repo/
  apps/console/        RouteLab console (Vite + TypeScript + React)
  apps/demo/           "Kitchen Table" demo app that reads routing from Remote Config
  packages/engine/     Pure TS eval engine (runner, graders, metrics, recommender) + unit tests
  functions/           (Optional) Cloud Function that publishes the Remote Config template
  datasets/            Small built-in test sets (JSON) + loader for Civil Comments
  remoteconfig.template.json   Generated by "Apply" (fallback publish path)
  firebase.json, .firebaserc, LICENSE (Apache-2.0), README.md
```

**Firebase products**

| Product                                              | Used for                                                                                                        |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| AI Logic (Gemini Developer API backend)              | Every model call. `getAI`, `getGenerativeModel`, `GoogleAIBackend`, `InferenceMode`, `response.inferenceSource` |
| App Check (reCAPTCHA Enterprise, debug token in dev) | Required by AI Logic. Debug tokens are accepted for judging                                                     |
| Firestore                                            | Projects, features, test sets, runs, per-case results                                                           |
| Auth (Google sign-in, or anonymous to start)         | Owner of projects; Firestore rules                                                                              |
| Remote Config                                        | Per-feature routing that the demo app reads                                                                     |
| Hosting                                              | Console + demo app, so judges get a URL                                                                         |
| Cloud Functions (optional, needs Blaze plan)         | Publishing Remote Config from the "Apply" button                                                                |

**Remote Config parameter (one per feature)**

```json
routing_<featureId> = {
  "mode": "PREFER_ON_DEVICE | ONLY_IN_CLOUD | PREFER_IN_CLOUD | ONLY_ON_DEVICE",
  "maxDeviceChars": 1200,        // inputs longer than this go to cloud (null = no split)
  "deviceTimeoutMs": 20000,      // abandon device call after this
  "cloudModel": "<billing-not-required model name>",
  "evidenceRunId": "<Firestore run id>"
}
```

**Firestore data model**

```
users/{uid}/projects/{projectId}
  features/{featureId}       { name, systemPrompt, userTemplate, outputSchema?, graderType, threshold }
  testsets/{testsetId}       { featureId, source, cases: [{ id, input, expected? }] }   // keep < 1 MB per doc; chunk if needed
  runs/{runId}               { featureId, testsetId, startedAt, status, env: { chromeVersion, nanoAvailability } }
  runs/{runId}/results/{caseId} { route: "device"|"cloud", output, inferenceSource, outcome, score, ms, tokens?, error? }
  runs/{runId}/summary       { device: {...metrics}, cloud: {...metrics}, recommendation }
```

## 3. Facts the build depends on (verified unless marked)

- Hybrid on web needs **Firebase JS SDK v12.5.0+** and **Chrome desktop 139+**. Competitor repos use SDK 13.x.
- Four modes: `PREFER_ON_DEVICE`, `ONLY_ON_DEVICE`, `PREFER_IN_CLOUD`, `ONLY_IN_CLOUD`. The response tells you which ran (`inferenceSource`).
- On-device (web) supports: single-turn text, text + JPEG/PNG image, structured output (JSON/enum), streaming. **Not** supported: multi-turn chat, audio/video/PDF, function calling, grounding, URL context. Multimodal max 9,216 tokens.
- Nano output languages: **en, ja, es, de, fr** only.
- Nano needs desktop Chrome, 22 GB free disk, GPU > 4 GB VRAM or 16 GB RAM + 4 cores. Not on Chrome Android/iOS. The first download needs a user gesture.
- **Observed on our test machine (Chrome 158):** about 5 s per moderation call; 6 parallel calls finished in 37 s total; one real toxic comment hung the model indefinitely, and after that every Nano call in the browser timed out until Chrome was restarted. Treat timeouts and health checks as core features.
- Remote Config: the **client SDK cannot write** templates. Publishing needs the Admin SDK / REST API (Cloud Function, Blaze plan) **or** `firebase deploy --only remoteconfig` with a template file referenced in `firebase.json`.
- _Unverified, check on Day 1:_ whether AI Logic's `generateContent` accepts an `AbortSignal` (if not, wrap in `Promise.race` with a timeout); whether Remote Config real-time updates (`onConfigUpdate`) work on web (if not, demo app uses `fetchAndActivate` with `minimumFetchIntervalMillis: 0` behind a "Refresh routing" button); the exact helper for triggering the Nano download (competitor repos call `initializeDeviceModel()` from a button click).
- Billing: pick cloud models marked **"billing not required"** in the AI Logic models list. Only request the Google Account Quota (Sprint 3 deadline **Wed 25 Nov, 10:00 AM PT = 11:30 PM IST**) if you decide you need a billed model.

## 4. Day-by-day plan

Each task lists: **goal**, **done when**, and **who should run it** (see section 7).

### Day 1 — Mon 23 Nov: setup and risky spikes

1. **Firebase project.** Create project, enable AI Logic (Gemini Developer API), Firestore, Auth (anonymous for now), Hosting. Register a web app. Set up App Check with reCAPTCHA Enterprise and a debug token. _Done when:_ a "hello" page on Hosting makes one cloud call through AI Logic with App Check enforced. _(Sonnet)_
2. **Hybrid spike.** In the hello page, create two models (`ONLY_ON_DEVICE`, `ONLY_IN_CLOUD`), call both with structured output, print `inferenceSource`, latency and `usageMetadata`. Add a "Download Nano" button. _Done when:_ both routes return JSON on the dev machine. _(Opus — unknown API surface)_
3. **Timeout/abort spike.** Prove we can abandon a stuck device call after N ms and detect a wedged model with a 15 s "health check" prompt. _Done when:_ forced timeout is caught and reported, page stays usable. _(Opus)_
4. **Remote Config publish spike.** Try path A (Cloud Function on Blaze using Admin SDK `getRemoteConfig().publishTemplate`). If Blaze is not possible, path B (write `remoteconfig.template.json` and run `firebase deploy --only remoteconfig`). Also test real-time vs fetch-on-click in a tiny client. _Done when:_ a parameter change shows up in a client. Write the decision into HANDOFF.md. _(Opus)_
5. **Monorepo scaffold.** Vite + TS + React for both apps, shared `packages/engine`, Vitest, ESLint/Prettier, Apache-2.0 LICENSE, GitHub repo public. _(Sonnet)_

### Day 2 — Tue 24 Nov: eval engine (no UI)

1. `packages/engine/runner.ts`: runs a test set for one feature. Device calls **sequential**, each with a timeout; before the run and after any timeout, run the health check; if unhealthy, stop device runs and mark remaining cases `skipped_unhealthy`. Cloud calls with concurrency 4. Emits progress events. _(Sonnet, from this spec)_
2. `graders.ts`: `exact`, `enum` (case-insensitive), `contains`, `jsonSchemaValid`, `regex`, and `refusal` detector (regex on refusal phrases + empty/invalid output). LLM judge stub (implemented Day 4). _(Sonnet)_
3. `metrics.ts`: per route — accuracy, refusal rate, schema-fail rate, timeout rate, p50/p95 latency, est. cloud cost (from token counts × a configurable price table; device = $0), and accuracy by input-length bucket. _(Sonnet)_
4. `recommend.ts`, deterministic rules (keep them simple and explainable):
   - Any device timeout or device refusal rate > 10% → `ONLY_IN_CLOUD`, reason shown.
   - Device accuracy ≥ feature threshold **and** ≥ cloud accuracy − 5 pts → `PREFER_ON_DEVICE`.
   - Else, if a length cutoff exists where device accuracy below it meets the rule above → `PREFER_ON_DEVICE` + `maxDeviceChars`.
   - Else → `ONLY_IN_CLOUD`.
     _(Opus writes the rules and tests; Sonnet can implement)_
5. Unit tests with fake model adapters for all of the above. _Done when:_ `npm test` is green. _(Sonnet)_

### Day 3 — Wed 25 Nov: console, part 1

1. Auth + Firestore rules (owner-only). _(Sonnet)_
2. Screens: Projects list → Project → Features (create/edit prompt, output schema, grader, threshold) → Test sets (paste lines, CSV upload, or load a built-in set). _(Sonnet)_
3. **Environment checker panel**: Chrome version, Nano availability, "Download Nano" button with progress, health check result, link to setup steps. _(Sonnet)_
4. Built-in sets in `datasets/`: (a) comment moderation using Civil Comments loaded at runtime from the Hugging Face datasets-server `rows` endpoint (toxic ≥ 0.8, borderline 0.4–0.6, clean = 0), with a cached fallback JSON; (b) short recipe summarisation with expected keywords; (c) structured extraction (recipe → JSON with ingredients/time). _(Sonnet; Opus checks dataset licence and labels)_
5. **Decision checkpoint:** do we need a billed cloud model? If yes, submit the quota form before 11:30 PM IST.

### Day 4 — Thu 26 Nov: console, part 2 (runs and reports)

1. Run screen: live progress, per-case rows streaming in, "device unhealthy, restart Chrome" banner. Results saved to Firestore. _(Sonnet)_
2. Report screen: side-by-side device vs cloud metrics, the verdict with plain-English reasons, accuracy-by-length chart, filterable table of failures with the exact input/output. _(Sonnet; Opus reviews wording)_
3. LLM judge (cloud, structured 1–5 score + reason) for features without expected answers, clearly labelled "estimated". _(Sonnet)_

### Day 5 — Fri 27 Nov: Apply + demo app

1. **Apply** button: builds the Remote Config parameters from the latest recommendation and publishes via the Day 1 path; records which run justified it. _(Sonnet)_
2. **Demo app "Kitchen Table"** (`apps/demo`): a small recipe community with two AI features — comment moderation and recipe summary. Each feature reads `routing_<featureId>`, builds the model with that mode, applies `maxDeviceChars` and timeout, shows a badge ("on-device" / "cloud", from `inferenceSource`), and a running cost counter. _(Sonnet)_
3. End-to-end test: run moderation and summary in the console → Apply → demo app switches. _Done when:_ this works three times in a row on a fresh profile. _(Opus debugs anything flaky)_

### Day 6 — Sat 28 Nov: product polish (Design criterion)

## 8. Top risks

| Risk                                              | Mitigation                                                                      |
| ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Judges see a dev tool as "not a product" (Design) | Onboarding, saved projects, polished report, demo app                           |
| Judges' machines lack Nano                        | Cloud-only mode works; video shows device path clearly; evidence stored in runs |
| Nano freezes mid-run                              | Sequential device calls, timeouts, health check, "restart Chrome" banner        |
| Remote Config publish needs Blaze                 | Fallback deploy path decided on Day 1                                           |
| LLM-judge scores disputed                         | Expected answers wherever possible; judge scores labelled "estimated"           |
| Scope creep                                       | Follow the cut list; no new platforms                                           |
